# Повторные измерения RebusSolver

Это отдельный измерительный проект для лабораторной № 2. Он не является пятой оптимизацией, не меняет историю Git и не заменяет исходник рабочего проекта `RebusSolver/main.c`.

## Запуск в Visual Studio 2022

1. Полностью распакуйте папку `RebusBenchmark` из архива. Не открывайте проект внутри ZIP.
2. Поместите её рядом с папкой `RebusSolver`:

```text
C:\Users\User\YP_Lab2\
    .gitignore
    README.md
    RebusSolver\
    RebusBenchmark\
        RebusBenchmark.sln
        RebusBenchmark.vcxproj
        benchmark.c
        bench_api.h
        wrappers\
        versions\
        sources_manifest.json
```

3. В Visual Studio используйте **Файл → Открыть → Проект или решение…**. Выберите `RebusBenchmark.sln`. Создавать новый проект не требуется.
4. Вверху выберите **Release / x64**. В проекте предусмотрена только эта конфигурация.
5. Выполните **Сборка → Собрать решение**, затем **Отладка → Запуск без отладки** (`Ctrl+F5`). Не запускайте под отладчиком: программа проверяет это и остановится с объяснением.
6. Дождитесь `BENCHMARK COMPLETE` и итоговой таблицы.

Оригинальные решатели, находящиеся в `versions`, не добавляйте в список компилируемых файлов: они уже включаются через адаптеры `wrappers`. Иначе возникнут повторные определения функций и несколько `main`.

При ошибке сборки не запускайте последнюю удачную сборку. Требуются установленные инструменты MSVC v143 и Windows SDK, как в использовавшемся ранее проекте.

На время измерения оставьте ноутбук подключённым к питанию, закройте игры, воспроизведение видео и другие тяжёлые задачи. Не меняйте режим питания между версиями. Приоритет процесса и привязка к ядру проектом не изменяются.

## Что сравнивается

| Метка | Версия |
|---|---|
| `baseline` | `RebusSolver_baseline_v2.c`, базовый итеративный перебор |
| `opt1` | Раннее отсечение ведущих нулей |
| `opt2` | Первое изменение и поразрядная проверка полной подстановки |
| `opt3` | Предыдущие изменения и предварительная подготовка разрядов |
| `opt4` | Предыдущие ограничения и схема разрядов, поиск с переносами |

Все пять исходников копируются из ранее переданных в переписке файлов без изменения байтов. Архив не выгружает коммиты с GitHub и не обращается к сети. Короткие ссылки на этапы из скриншотов и SHA-256 включённых файлов записаны в `sources_manifest.json`. Хеши относятся к этим копиям, а не автоматически к файлам внутри Git-коммитов: сохранение в Visual Studio могло менять переносы строк и кодировку.

Использована именно переработанная базовая версия **baseline_v2**, которая проверялась и сохранялась перед оптимизациями, а не более ранний рекурсивный черновик.

В каждой обёртке `REBUS_LIBRARY=1` исключает демонстрационный `main`. Макрос переименовывает только внешнюю функцию, чтобы собрать пять версий в одной программе. Алгоритмический код не меняется. `UNIQUE_DIGITS=1` одинаково у всех версий. Это прежнее рабочее допущение: разные буквы соответствуют разным цифрам; цифры, уже записанные во входе, не занимают позиции букв.

## Протокол измерений

Число серий и устройство стенда выбраны для нашего эксперимента. Методичка требует сравнения быстродействия, но не устанавливает именно такой протокол.

- Используются те же пять ребусов, что на предыдущих скриншотах.
- Перед замерами выполняется по одному прогревочному вызову каждого алгоритма на каждом тесте. Ответ проверяется независимой функцией: равенство, согласованность букв, различие цифр у разных букв и отсутствие ведущих нулей. Этот валидатор предназначен для коротких пяти тестов стенда, а не для произвольных 511-символьных чисел.
- Число повторений подбирается отдельно для каждой пары «алгоритм / ребус». Калибровка удваивает размер пакета до приблизительно 50 мс или до 1 048 576 вызовов. Целевые 50 мс относятся к калибровке, а не гарантированной длине каждого последующего пакета.
- После калибровки число повторений фиксируется. Выполняются **9 измеряемых серий для каждой из 25 пар**, всего 225 строк сырых результатов. Это не только девять одиночных запусков: быстрый решатель вызывается в пакете много раз.
- Между сериями циклически изменяется порядок тестов и алгоритмов. Параллельного запуска версий нет.
- Для каждого пакета измеряется полное время, затем делится на число вызовов. Выводится **медиана девяти средних времён одного вызова в пакете**, дополнительно сохраняются минимум и максимум.
- Частота `QueryPerformanceCounter` запрашивается один раз при старте. Сам таймер вызывается два раза на пакет. В контрольной POSIX-сборке используется `CLOCK_MONOTONIC`.
- Внутри замера: полный вызов `solve_rebus`, включая разбор строки, подготовку схемы, поиск, сбор статистики и создание строки ответа. Время небольшого адаптера, цикла и чтения результата тоже включено и не вычитается.
- Печать, независимая проверка ответа, сравнение счётчиков с прогревом и запись в файлы выполняются после остановки таймера. Проверяется последний ответ каждого измеренного/калибровочного пакета; успешность возврата проверяется в каждом вызове.
- Все исходники компилируются одним MSVC в одной конфигурации **Release / x64**, `/O2`, C11, UTF-8, `/MD`, защита стека. `/GL` отключён для всех; обёртки объявлены `noinline`. Результаты используются, чтобы избежать удаления ненужных вычислений компилятором.
- Все итоговые версии измеряются заново. Таблица не объединяет новые серии с прошлыми одиночными запусками. Настройки отдельного проекта могут отличаться от прежних настроек Release рабочего проекта.

Для каждого алгоритма ищется **первое правильное решение**, как предусмотрено заданием. Оно может отличаться между версиями, в частности после изменения порядка поиска в opt4. Счётчики узлов полезны для описания поиска, но работа одного узла различается; отношение количества узлов не равно коэффициенту ускорения.

Повторение не устраняет полностью влияние нагрузки ОС, температуры, частоты процессора и состояния кэшей. При большом разбросе следует повторить весь эксперимент в спокойных условиях и сохранить обе серии результатов, не выбирать только выгодные значения.

## Результаты

Рабочая папка при запуске из Visual Studio задана как папка проекта. После успешного выполнения здесь появится:

```text
RebusBenchmark/results/run_YYYYMMDD_HHMMSS_UTC_PID/
    environment.txt
    solutions.txt
    raw.csv
    summary.csv
    summary.txt
```

Каждый запуск создаёт отдельную папку. Имеющиеся результаты не перезаписываются. Временная метка используется только в названии папки и не участвует в измерении скорости. При запуске другим способом `results` создаётся в текущей рабочей папке процесса.

`environment.txt` содержит версию компилятора, разрядность, частоту таймера, доступные сведения о процессоре, объёме памяти и подключении питания, а также протокол измерений. Адреса электронной почты, имя учётной записи и имя компьютера программа не собирает.

`solutions.txt` содержит вход, найденный ответ и счётчики для 25 пар. `raw.csv` содержит все измеренные пакеты и сырые значения таймера. `summary.csv` содержит 25 итоговых строк. Разделитель CSV — запятая, десятичный разделитель — точка. `summary.txt` содержит удобную таблицу для просмотра и снимка экрана.

Коэффициент в столбце `speedup_vs_baseline` вычисляется отдельно для каждого ребуса: медианное время базовой версии / медианное время рассматриваемой версии. Это измерение на выбранном наборе входов и данном компьютере, не гарантия ускорения на любом ребусе.

Если программа завершилась с ошибкой или без `BENCHMARK COMPLETE`, результаты считаются неполными. Не использовать их как завершённый эксперимент.

## После запуска

Сохраните снимок итоговой таблицы и отправьте новую папку `run_...` целиком в ZIP. Проект `RebusSolver` и его `main.c` не изменяйте. Измерительный проект и проверенные журналы можно сохранить позднее отдельным техническим коммитом, не называя его ещё одной алгоритмической оптимизацией.

## Контрольная сборка вне Windows

Для проверки самого стенда предусмотрен `build_posix.sh`. Он не нужен для работы в Visual Studio. Результаты тестового Linux-запуска не являются измерениями пользователя в MSVC.

В поставку не включены готовые исполняемые файлы или результаты чужого компьютера. Все пользовательские измерения появятся только после локальной компиляции и запуска.
